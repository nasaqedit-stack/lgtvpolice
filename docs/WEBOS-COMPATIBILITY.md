# توافق مشغل `/player` مع webOS 3.5 (LG UJ634V)

هذا المستند يوثّق سبب تعطّل المشغل السابق على تلفاز LG UJ634V، والإصلاح المُطبَّق،
وطريقة التحقق، والحدود المتبقية. المشغل الحالي مستقل تماماً عن حزمة Next.js
الخاصة بلوحة الإدارة، ولم تتغير أي واجهة برمجية أو سياسة أمان.

## 1. العطل الفعلي (خلفية تقنية)

متصفح تلفاز UJ634V على webOS 3.5 هو **Chromium 38**، أي محرّك **ES5 فقط**:

| القدرة | الحالة على webOS 3.5 |
| --- | --- |
| `globalThis` (Chrome 71+) | غير موجود |
| `?.` و `??` و `\|\|=` (Chrome 80/85+) | غير مدعوم — خطأ صياغة |
| دوال السهم و `let/const` و `class` | غير مدعومة (خطأ صياغة) |
| `AbortController` (Chrome 66+) | غير موجود |
| `ResizeObserver` / `IntersectionObserver` / `BroadcastChannel` | غير موجودة |
| `Blob.prototype.arrayBuffer` (Chrome 76+) | غير موجود |
| `crypto.subtle` | موجود شكلياً لكن غير موثوق على هذا الإصدار |
| `fetch` (Chrome 42+) | غير موجود |
| Service Worker / PWA | غير مدعوم |
| MediaSource | قديم وجزئي — لا يُعتمد عليه |

كان المسار `/player` صفحة React داخل App Router، وأول رسم لها يتطلب نحو
**590 كيلوبايت** من حزم ES2020/ES2022، وكل حزمة تبدأ بدالة سهمية وتستخدم
`globalThis`. النتيجة: **خطأ صياغة فوري قبل تحميل React**، فتبقى الشاشة فارغة أو
متجمدة ولا يعمل أي زر ولا الربط ولا المزامنة.

## 2. الإصلاح

`/player` أصبح مستند HTML ثابتاً صغيراً (~10 كيلوبايت) يُخدَّم من الحافة
(`app/player/route.ts` → `lib/player/standalone/shell.ts`) ويحمّل ثلاثة ملفات
ES5 كلاسيكية فقط:

| الملف | الوظيفة |
| --- | --- |
| `public/player/sha256.js` | SHA-256 تزايدي بـ ES5 خالص (بدل `crypto.subtle` و`Blob.arrayBuffer`) |
| `public/player/runtime.js` | كشف القدرات، التخزين، الشبكة، المزامنة، محرّك التشغيل |
| `public/player/player.js` | واجهة عربية RTL: الربط، التقدم، شريط الحالة، شاشة التشخيص |

استُخدمت نفس واجهات الإدارة كما هي دون تغيير: `POST /api/player/pair`،
`GET /api/player/manifest` مع `If-None-Match`/304، `POST /api/player/media-urls`،
`GET /api/player/media/<mediaId>` مع `Range`، و`POST /api/player/heartbeat`.
التخزين المحلي يستخدم نفس قاعدة `digital-signage-player` بنفس المخازن، لذلك
تلفاز مربوط سابقاً يحفظ اعتماده ووسائطه.

### استراتيجية التوافق

- **الفصل الكامل** عن حزمة Next.js: لا `/_next/` ولا `type="module"` في صفحة التلفاز.
- **ES5 فقط**: يتحقق `tests/player-standalone-syntax.test.ts` بمحلّل acorn بإصدار
  `ecmaVersion: 5` من كل ملف يُخدَم، ويرفض دوال السهم و`?.` و`??` و`globalThis`
  و`Object.assign` و`Array.from` و`Promise.finally` وغيرها.
- **كل قدرة اختيارية لها بديل**: IndexedDB ← Cache API ← الذاكرة؛ `fetch` ← XHR؛
  `Blob.arrayBuffer` ← FileReader؛ `Intl.formatToParts` ← `toLocaleString`؛
  Promise داخلية إن لم توجد Promise أصلية.
- **لا شيء إلزامي غير الرسم**: Service Worker وPWA وMediaSource كلها غير مطلوبة،
  وغيابها لا يمنع ظهور الواجهة.
- **لا شاشة فارغة أبداً**: المستند يرسم لوحة عربية ورابط "إعادة المحاولة" قبل
  تشغيل أي سكربت، و`__signageGuard` يكشف التعارض بعد 15 ثانية أو عند فشل تحميل
  أي ملف، مع عرض المتصفح وChromium والقدرات والحالة.
- **شاشة تشخيص عربية** على `/player?diag=1` (أو من شريط الحالة أو زر INFO):
  «مشغل الشاشة غير متوافق مع إصدار المتصفح الحالي» مع معلومات المتصفح والقدرات
  وسجل آخر الأحداث وزرّي «إعادة المحاولة» و«إعادة التحميل».

## 3. النتائج

```
npm test         → 14 ملفاً، 177 اختباراً ناجحاً
npm run lint     → نظيف، بلا تحذيرات
npm run typecheck → نظيف
npm run build    → ناجح، و /player مسار ثابت (○)
```

الاختبارات الجديدة تشغّل **الملفات المُخدَّمة فعلاً** داخل jsdom بنافذة تحاول
تقليد webOS 3.5 (بلا `AbortController`/`ReadableStream`/`indexedDB`/`fetch`/
`Blob` URLs)، وتغطي: الرسم بدون واجهات حديثة، حماية الشاشة الفارغة، بدائل
التخزين، الربط، إعادة استخدام 304، فشل الشبكة والبيانات التالفة ونفاد المساحة،
تشغيل صورة ثم MP4، إعادة استخدام عنصر الفيديو عبر الانتقالات بلا فرض mute،
إخفاء واجهة التشغيل، تفعيل الصوت وحفظ التفضيل، فحص حاوية MOV، حارس التوقف،
والتشغيل من المخزون بعد إعادة تشغيل بلا إنترنت.

نتائج الإنتاج المسجلة أدناه تخص النسخة المنشورة السابقة، ولا تُثبت نشر هذا التغيير:

- `https://lgtvpolice.vercel.app/player` أعاد 200 بمستند ~10 كيلوبايت في الفحص السابق.
- تشغيل الصفحة في متصفح حقيقي عرض واجهة الربط العربية وشريط الحالة بلا لوحة تعارض في الفحص السابق.
- `/player/runtime.js?v=2.0.0-1` خُدّم كـ ES5 صحيح في الفحص السابق.
- فحوص الإنتاج للوسائط: نقطة التخزين و CORS ناجحة (`Production media E2E`) في الفحص السابق.
- فحص مخطط حِمل الربط المرسل من المشغل ناجح (`pairing E2E` → البند 0) في الفحص السابق.
- نشر النسخة `2.2.0-1` والتحقق الإنتاجي منها واختبار LG UJ634V: لم يتم بعد
  (التحقق تم محلياً على `npm run build && npm start`، وللفحص الإنتاجي يجب دمج
  التغيير في `main` ثم فتح `/player?diag=1` على التلفاز).

## تحديث مشغل العرض وسبب التعتيم/المقاس (2026-10-08)

**السبب الذي يمكن إثباته من كود المشغل السابق:** كانت طبقة `.sp-overlay` تبقى فوق المسرح أثناء playback، و`paint()` يضع عليها `sp-overlay-quiet` حتى عندما تكون فارغة. خلفيتها `rgba(5, 10, 18, .82)` فتغطي الوسائط بنسبة عتامة تقارب 82% وتُظهرها داكنة. كان هذا تعتيماً من التطبيق، لا دليلًا على أن إعداد التلفاز هو السبب الوحيد. في المعاينة الحديثة كانت شاشة الانتقال تعرض أيضاً fallback داكناً أثناء جلب العنصر.

**سبب عدم تغطية الشاشة:** `.sp-media` و`.sp-video` كانا متمركزين عند 50% مع `max-width/max-height` فقط ومن دون أبعاد viewport أو `object-fit: cover`. هذا يجعل المتصفح يستخدم الحجم/النسبة الذاتية للمصدر وقد يترك فراغاً حوله. احتوى مسار المعاينة كذلك على `object-fit: contain`.

**الإصلاح في هذا التغيير:** ملفات CSS داخل HTML المستقل تعطي الصورة والفيديو `position: fixed; top: 0; left: 0; width: 100vw; height: 100vh; margin/padding/border: 0; object-fit: cover`. الخلفية سوداء تحت العنصر فقط. يُخفى overlay وشريط الحالة بعد بدء التشغيل ولا توضع طبقة شفافة فوق الصورة. واجهة الربط/التشخيص لا تظهر في العرض العادي. المشغل يحتفظ بعنصر `<video>` واحد ويغير مصدره فقط عند تغيره، ويوقفه/يخفيه عند الانتقال للصورة. يضبط `muted=false` و`volume=1` ولا يضيف attribute `muted`.

إذا رفض Chromium تشغيل الفيديو بصوت autoplay، تظهر أداة واحدة «تشغيل الصوت»؛ الضغط عليها يستدعي `play()` مباشرة داخل تفاعل المستخدم ويحفظ التفضيل في مخزن metadata المحلي. MOV ليس مقبولاً بمجرد امتداده: يفحص متصفح الرفع Atom metadata بحثاً عن فيديو H.264 (`avc1`/`avc3`) وصوت AAC-LC (ESDS/`mp4a.40.2`) إذا وجد مسار صوت، ويتحقق من قراءة metadata. ثم يعيد API فحص `ftyp`/`moov` من الملف المكتمل عبر byte-range قبل إنشاء سجل المكتبة؛ اختبار forged-client يؤكد أن ادعاء `candidate` لا يتجاوز رفض HEVC. يُرفض codec مجهول مع تعليمات التحويل إلى MP4/H.264/AAC. يثبت ذلك بنية codec المعروفة فقط، ولا يضمن فك الترميز على Chromium 38 في التلفاز.

**حدود العتاد:** إزالة طبقة CSS تعالج تعتيماً برمجياً موجوداً فعلاً، لكنها لا تثبت أن أي تعتيم متبقٍ من تلفاز UJ634V قد اختفى. لا تعرض صفحة الويب في Chromium 38 واجهة معيارية للتحكم بسطوع اللوحة أو إعدادات Eco/screen saver، وواجهة Wake Lock الحديثة غير متاحة لهذا الهدف. واجهة متصفح التلفاز الخارجية أيضاً لا تستطيع الصفحة إخفاءها؛ يمكنها فقط محاولة fullscreen بعد تفاعل المستخدم. يجب اختبار إعدادات التلفاز والسطوع على الجهاز الحقيقي.

## تحديث «التشغيل أولاً» ومقاومة انقطاع الإنترنت (2026-10-08، النسخة `2.2.0-1`)

**المشكلة:** كان مسار البدء ينتظر كل شيء قبل أول إطار: `getStats` و`countCachedAssets`
و`getSeenReloadVersion` و`getAudioEnabled` تُقرأ كلها في `P.all` واحد مع الشهادة والبيان،
ثم تُنفَّذ المزامنة. وكان `paint()` يعرض طبقة `.sp-overlay` المعتمة عندما
يكون `showPairForm` صحيحاً حتى لو كان المحتوى يلعب، وواجهة الربط تُفرض بعد كل 401.
كما أن `applyManifest()` كان يستدعي `render()` بعد كل مزامنة، فيُعاد إنشاء كائن الـ blob
ويُعاد ضبط `src` على عنصر الفيديو ⇒ **يتوقف التشغيل ويعود إلى الصفر كل 60 ثانية**.
وكان `deleteUnreferenced()` يحمي فقط وسائط القائمة السابقة، فيمكن أن يحذف الوسيط
الذي يُعرض حالياً عند تفعيل قائمة جديدة. وكان حارس التوقف ينتقل للعنصر التالي مباشرة
بلا محاولة استعادة، والعنصر غير المخزّن يقفز فوقه المشغل بينما يحذف العنصر المعروض
من المسرح في مسار فشل الوسائط ⇒ شاشة سوداء.

**القاعدة المطبقة الآن: `PLAYBACK > CACHE > SYNC`** — الشبكة ليست شرطاً لاستمرار
العرض بعد نجاح التخزين:

1. **بدء فوري**: `start()` ينتظر فقط `getCredential` + `getActiveManifest`
   (+ حالة التشغيل المحفوظة)، ثم `attachEngine()` يرسم من البيان المحلي والوسائط
   المخزنة، ثم تبدأ المزامنة في الخلفية (`backgroundWork`). لا حجب على Vercel ولا
   Supabase ولا المصادقة ولا أي طلب بيان.
2. **الترتيب حسب الأولوية**: البيان المحلي ← الوسائط المخزنة ← التشغيل ← المزامنة
   الخلفية ← التنزيل والتحقق ← تفعيل ذري ← أو البقاء على القائمة الحالية.
3. **صفر مقاطعة أثناء المزامنة**: `render()` لا يعيد تركيب العنصر المعروض أبداً
   (`mountedHash`/`mountedKind`)، و`applyManifest()` لا يستدعي `render()` إذا لم
   يتغير `manifestHash`، وتُخزَّن عناوين `blob:` لكل بصمة في `sourceCache` فتُعاد
   ولا يُقرأ الملف من IndexedDB مرة أخرى ولا يُعاد `load()` للفيديو.
4. **لا شاشة سوداء**: عند فقدان الوسيط التالي يُبقى العنصر المعروض على المسرح
   ويُعاد المحاولة بالتراجع (5s→10s→20s→40s→60s، 6 محاولات) قبل تجاوز العنصر،
   وتُطبق تقنية الصورة المعلّقة (تُحمَّل مخفية ثم تُظهر) وفي مسار فشل الوسائط
   يبقى العنصر السابق ظاهراً حتى تصبح البديل جاهزاً.
5. **GC لا يمس النشط**: `createSync({ protectHashes })` يضيف وسائط القائمة المعروضة
   والعنصر الحالي إلى قائمة الحماية في كل تمرير، ويُنفَّذ التنظيف بعد التفعيل
   (بلا حماية) فعلاً فقط بعد أن يتخلى المحرّك عن القائمة القديمة، وكذلك في مسار 304.
6. **استعادة الأعطال**: حارس التوقف يعيد تهيئة عنصر الوسائط محلياً (pause/load/play)
   ثم يعيد قراءة الوسيط من IndexedDB (`rebindLocalMedia`) قبل أن يتخطى العنصر؛
   وحارس الواجهة كل 15 ثانية يعيد `render()` بعد 30 ثانية من مسرح فارغ، ويسمح
   بإعادة تحميل واحدة **مُقنَّنة** (نافذة 10 دقائق محفوظة في `meta.recoveryReload`)
   فقط إذا كان هناك وسيط محلي سبق عرضه — فلا حلقة إعادة تحميل أبداً.
7. **استئناف بعد إعادة التحميل**: `meta.playbackState` يحفظ
   `{manifestHash, playlistId, index, hash, kind, positionMs}`، فيُستأنف العنصر نفسه
   (وموضع الفيديو إن كان صالحاً) بلا شبكة.
8. **مهل وتراجع**: كل طلب في المشغل له `timeoutMs` (بيان 20s، روابط 15s، صوت 20s،
   وسائط 180s)، والمزامنة تتراجع أسّياً (60s → 10 دقائق حداً أقصى) ولا تحجب الرسم.
9. **المؤشر لا يغطي المحتوى**: شريط الحالة مخفي أثناء العرض، والربط لا يُفرض فوق
   محتوى يعمل (يُتاح من زر «إعادة ربط الشاشة» في شاشة التشخيص)، والفشل `fatal` لا
   يفتح شاشة الخطأ إذا كان هناك وسيط على المسرح.

**الاختبارات**: `tests/player-offline-first.test.ts` (17 اختباراً) تشغّل المستند
والملفات المُخدَّمة فعلاً في نافذة شبيهة بـ webOS 3.5 وتغطي: بدء المخزون بفشل كل
الطلبات، عدم إرسال أي طلب وسائط أثناء العرض، فشل البيان بلا مقاطعة، إلغاء الربط
بلا استيلاء شاشة، تفعيل ذري، حماية GC، فقدان العنصر التالي بلا شاشة سوداء،
حارس التوقف، الاستئناف بعد إعادة التحميل، عودة الشبكة، والتحقق من عدم وجود
حلقة إعادة تحميل. كما اختُبر مسار الإنتاج محلياً: `npm run build && npm start`
ثم فتح `/player` المُخدَّم مع تخزين مُعبّأ مسبقاً وواجهة API معطلة ⇒ ظهرت الوسائط
من `blob:` وبقي `sp-overlay` مخفياً.

## 4. حدود متبقية

1. **التأكيد على الجهاز نفسه لم يحدث بعد**: لا يمكن تنفيذ ذلك من بيئة التطوير.
   المطلوب فتح `/player?diag=1` على التلفاز وإكمال قائمة التأهيل في
   `docs/TV-SETUP.md` (ربط، مزامنة، تشغيل صورة، تشغيل MP4، فصل الشبكة، إعادة تشغيل).
2. **إعادة تحميل واحدة قد تلزم** لتلفاز كان قد حمّل النسخة القديمة ومعها Service
   Worker قديم يحفظ الصفحة: العامل الجديد يمسح التخزينات القديمة ويخدم التنقل
   بنمط «الشبكة أولاً»، لذلك التحميل التالي يكون صحيحاً.
3. **فيديو تدريجي فقط**: لا MediaSource؛ MP4 يجب أن يكون H.264/AAC قابلاً للتشغيل المباشر. يُقبل MOV فقط بعد فحص H.264/AAC في متصفح الإدارة، لكن تشغيله على webOS 3.5 غير مضمون من دون اختبار الجهاز. التنزيل يتم بأجزاء 4 م.ب إلى IndexedDB، والتحقق قبل التشغيل.
4. **حد 192 م.ب** يخص فقط مسار «جلب الملف كاملاً في الشبكة» عند غياب المخزون
   المحلي؛ الملفات المخزّنة لا تخضع لهذا الحد.
5. **بلا IndexedDB ولا Cache API** يعمل المشغل من الذاكرة: العرض يستمر لكن
   التنزيل يتكرر بعد كل إعادة تحميل.

## 5. ما لم يُلمس

لوحة الإدارة، ورفع الوسائط، ومشروع Supabase، وأمان الربط، وأمان تخزين الوسائط،
ونشر قوائم التشغيل، ورؤوس الأمان في `next.config.ts`، وشهادة TLS — كلها كما هي.
المعاينة على متصفح حديث متاحة على `/player/preview` (تنفيذ React السابق).
